# Blind Spots — что проверить НЕ удалось и почему

Честный список границ этого аудита. Каждый пункт — что именно осталось непроверенным фактически и что нужно для проверки.

## 1. Фактический WMAPE/MASE на реальных данных `Dataset/1c_*.csv` — НЕ ПЕРЕСЧИТАН на живой модели
- **Почему:** обучение требует LightGBM/libomp (память: ML-тесты падают локально на `dlopen libomp.dylib`), + локальные версии библиотек дрейфуют от pinned (fastapi/pydantic/sklearn, см. `reproduction.md`), + полный ансамбль ~37 мин и нужен прод-конфиг.
- **Что проверено вместо этого:** формулы метрик (независимый прогон, совпало) + вся пайплайн-логика чтением тела. Утверждения о СМЕЩЕНИИ метрики (M-A1/A5/A6) доказаны логически/численно на синтетике, но абсолютная цифра на 1C не измерена.
- **Для проверки:** на Linux-CI/staging с pinned-deps прогнать `run_training_pipeline` на `1c_train.csv`, сравнить headline-метрику с (а) honest holdout без HPO и (б) seasonal-naive(7) на том же holdout.

## 2. Полный прогон pytest / mypy / lint — НЕ ВЫПОЛНЕН
- **Почему:** локальное окружение не воспроизводит CI (нет pytest-asyncio → async-тесты не идут; version drift; многие ML-модули SKIP на libomp; тесты требуют БД/Redis/S3-стабов). Прогон дал бы недостоверную картину (false fail/skip).
- **Проверено:** `pytest --collect-only` = 1143 теста собрались без ошибок коллекции; качество ассертов проверено чтением (TEST-1…TEST-5).
- **Для проверки:** прогнать в Linux-CI образе из `docker/`, снять реальный coverage инструментом (а не «на глаз»).

## 3. Реальный запуск приложения и live-трассировка запросов — НЕ ВЫПОЛНЕН
- **Почему:** требует Postgres + Redis + Lockbox/секреты + S3 (Beget) + MLflow; read-only аудит без поднятия инфры.
- **Проверено:** контракты API и блокировка event-loop — статически (чтение роутеров). 
- **Для проверки:** поднять `docker compose` стенд, замерить латентность `/predict` под параллельной нагрузкой (подтвердить ASYNC-1 практический импакт на конкретном прод-host sizing).

## 4. Frontend (`corefundev/frontend`) — НЕ АУДИРОВАН
- **Почему:** скоуп этого захода — backend (ML-точность приоритет). Frontend синхронен с remote (`91f0f41`), но его код, как клиент API, не проверялся на обработку 3 форм error-envelope (CONTRACT-2) и batch-all-or-nothing (CONTRACT-batch).
- **Для проверки:** отдельный заход по frontend.

## 5. Динамические/рефлексивные вызовы — частично
- **Почему:** dead-код (DEAD-1…3, INFO-dead-*) подтверждён grep'ом реальных ссылок, но rq-job'ы вызываются по строковому имени/реестрам — есть остаточный риск ложно записать «живое» в «мёртвое».
- **Проверено:** для каждого dead-claim finder приводил grep; `_batch_inference_job`/`get_limiter` — ноль enqueue/ссылок. Считаю надёжным, но не на 100% (нет динамического трейсинга прод-воркеров).

## 6. Инфраструктура (docker/ansible/migrations/scripts) — вне фокуса
- **Почему:** 33 docker-каталога, ansible, 18 migrations, ~51 скрипт. Память фиксирует обширную инфра-историю (R7/R10/R11). Этот аудит сфокусирован на `src/` (приложение + ML). Миграции не проверены на атомарность/откат фактически.
- **Для проверки:** отдельный инфра-проход; для migrations — прогон up/down на тестовой БД.

## 7. CVE по lock-файлам — НЕ СКАНИРОВАНО инструментом
- **Почему:** не запускал OSV/pip-audit в этом заходе. Версии в `requirements.txt` несут ручные CVE-аннотации (lightgbm 4.6 RCE-fix, sklearn 1.5.2 CVE-2024-5206, starlette/multipart), но независимый OSV-скан не проводился.
- **Для проверки:** `osv-scanner`/`pip-audit` по `requirements.txt` + `requirements-dev.txt` на актуальной БД уязвимостей.

## 8. История git на секреты — НЕ СКАНИРОВАНА
- **Почему:** проверка `git log -p` на захардкоженные секреты в истории не выполнялась (фокус на текущем состоянии). Текущий код: secrets через Lockbox/env (греп не нашёл живых ключей в `src/`).
- **Для проверки:** `gitleaks`/`trufflehog` по полной истории `backend`.

## 9. Конкурентность под реальной нагрузкой — статически
- Гонки (ASYNC-race RateLimiter) и атомарность rate-limit/OTP подтверждены чтением, но не стресс-тестом. Реальные race-окна не воспроизводились нагрузкой.
